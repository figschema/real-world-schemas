# Ghost database schema

> 🚧 **In progress** - captured, being arranged. This banner disappears when the diagram lands.

The database behind the publishing platform: 97 tables, 109 foreign keys with explicit delete rules, and the disciplined opposite pole of the WordPress entry - integrity lives in the engine, not the application.

## What's interesting

- **The anti-WordPress.** Where WordPress enforces nothing in the engine, Ghost declares 109 foreign keys and spells out the delete semantics on each: `ON DELETE CASCADE` removes a member's subscriptions, events and labels when the member goes. The database does the bookkeeping.
- **Event sourcing as a habit.** Dozens of `members_*_events` tables - created, status, payment, login, click events - every state change to a member is an append-only fact, not an UPDATE. History is a first-class citizen.
- **The transactional outbox.** An `outbox` table with `event_type`, `status` and a `payload` - events are written transactionally alongside the data change and drained asynchronously. The classic distributed-systems pattern, visible in one small table.
- **Foreign keys to non-key columns.** `gift_link_token` references `gift_links.token` - a FK whose target is a unique but decidedly non-`id` column, so cascade rules ride on a token string.
- **191, again.** Ghost's own size guide: "Medium strings = length 191" - the same utf8mb4 index-length heritage WordPress carries, independently re-derived.
- **Views in the box.** Ghost also ships SQL views - the members' current-subscription view encodes the subscription state machine (abandoned 3DS checkouts excluded) as SQL rather than application code.
