# Matomo database schema

## What's interesting

- **The archive tables that aren't there.** A fresh install creates 26 tables - and deliberately skips `archive_blob` and `archive_numeric`: the installer code unsets them, because the archiver creates dated archive tables lazily, one pair per month. The schema is designed to grow with the data.
- **`log_visit` is a 6-column spine.** The wide tracking table of Matomo 3 (dozens of `config_*` columns) has been slimmed to the essential visit identity - idvisit, idsite, idvisitor, visit_last_action_time, config_id, location_ip - with MySQL 8 **descending indexes** (`(..., visit_last_action_time DESC)`) tuned for the exact queries the reports run.
- **Zero foreign keys, like WordPress.** Referential integrity is enforced in PHP - `log_link_visit_action` rows point at `log_visit` and `log_action` by convention, not by constraint.
- **Everything is prefixed.** Every table carries the `matomo_` prefix so the analytics stack can share a database with a blog or CMS - coexistence is a schema decision, not an afterthought.
- **Security and ops are first-class tables.** `brute_force_log`, `session`, `locks` (with a VARCHAR(70) key sized by a class constant), `tracking_failure`, and `archive_invalidations` - the operational concerns of a self-hosted product are modeled in the core schema.
- **Plugin tables are not here.** This is the core schema only - bundled plugins (Goals beyond `goal`, Forms, CustomDimensions...) add their own tables at install. The gallery captures what the installer itself creates.
