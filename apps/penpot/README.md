# Penpot database schema

> ![Penpot database schema - ER diagram](schema.svg)

The database behind the open-source design-and-prototyping platform: 59 tables, 65 foreign keys with real engine-level integrity, and file data sharded across sixteen physical tables.

## What's interesting

- **File data is sharded sixteen ways.** `file_data_00` through `file_data_15` are sixteen physical tables holding design-file blobs, distributed by hash - a single logical store spread wide because design files are enormous and Postgres tables do not love giant rows. `file_data_fragment` tracks which backend each fragment lives in (the schema abstracts over S3 vs database storage).
- **Real referential integrity, finally.** 65 foreign keys with cascade rules - the whole permission triangle (`team_profile_rel`, `project_profile_rel`, `file_profile_rel`) is enforced by the engine, not application code.
- **Rel-tables instead of join columns.** Every membership and access rule is a dedicated `_rel` table - team-to-profile, project-to-profile, file-to-profile - a normalized permission matrix rather than a role column.
- **The migration set ships a manual-intervention migration.** The tree's `XXXX-drop-obsolete-tables.sql` is a Penpot convention for cleanup applied only by hand - the fresh-install capture correctly excludes it. (The tree also contains a byte-identical duplicate of migration 0122 under two names; applied once.)
- **Ops tables read like a SaaS checklist.** `sso_provider`, `webhook` + `webhook_delivery`, `http_session` alongside `http_session_v2` (a session migration carried in-schema), `scheduled_task` + history, `audit_log`, `usage_quote`, and two complaint-report tables.
