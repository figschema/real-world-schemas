# Mastodon database schema

The database behind the largest decentralized social network: 116 tables, 156 foreign keys, time-ordered IDs generated by a database function, and federation moderation carved into the schema itself.

## What's interesting

- **IDs that tell time.** `accounts.id` is `bigint DEFAULT timestamp_id('accounts')` - a database function generating snowflake-style, time-ordered identifiers. Your account number literally encodes the moment it was created, sorted for free.
- **The anti-WordPress, taken further than Ghost.** 156 foreign keys, and 148 of them carry explicit delete rules - 124 `ON DELETE CASCADE`, 24 `SET NULL`. Deleting a user cascades through the federation graph without a single line of application cleanup.
- **Deleted accounts become tombstones.** The `tombstones` table keeps the URI and the fact that something *used to exist* - so remote servers know a deleted account was real, not a hallucination. Distributed systems need memory of absence.
- **Federation moderation is schema-level.** `domain_blocks`, `domain_allows`, and `email_domain_blocks` are first-class tables: entire servers can be silenced or suspended by rows, not config files.
- **Postgres arrays as first-class columns.** `bigint[]` and `varchar(255)[]` columns (with defaults like `'[]'`) hold ordered lists inline - a deliberate denormalization most schemas reach for only in a pinch.
- **The schema knows its own releases.** `software_updates` and `software_deprecations` track version metadata and end-of-life markers as data.
